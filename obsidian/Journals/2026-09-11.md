# 2026-09-11: piper_memory built end-to-end, first real result confirms yesterday's prediction

New branch, `feature/piper-memory`, based on `main` rather than
`feature/reasoning-geometry` - genuinely separate track (a measurable
curiosity/learning-progress mechanism for Piper, not cross-model
translation). Full architecture design happened yesterday
(`obsidian/Journals/2026-09-10.md` on the reasoning-geometry branch);
today was building it.

## What got built

**`MemoryStore`** (`src/piper_memory/memory_store.py`) - in-RAM resident,
disk-persisted. Ordered items (topic, content, timestamps, an
append-only loss history) with embedding matrices per method kept
positionally aligned. Brute-force cosine similarity search, deliberately
not FAISS - at the intended scale (hundreds to low-thousands of items)
it's sub-millisecond, and keeping the mechanism fully inside inspectable
code was an explicit design choice from yesterday's discussion, not a
simplicity shortcut. Persistence split by existing project convention:
`torch.save`/`load` for embeddings, JSON for metadata. `load()` on a
missing path returns a fresh, empty store rather than raising - first-
ever run is expected, not an error, since "start limited, learn and
retain" depends on that being true. `add_or_update_item` treats an
existing topic as a re-study (refresh content/embedding in place,
`first_learned` and `loss_history` untouched); `learning_progress`
returns `None` with fewer than two measurements rather than `0.0`, so
"not enough data" stays distinguishable from "measured no change." Full
synthetic test suite, 9 cases.

**`fictional_entities`** (`src/piper_memory/fictional_entities.json` +
`.py`) - the warble/quaddle fabricated-knowledge content designed
yesterday. Warbles (role "studied", 10 facts) is what the mechanism gets
to learn about; quaddles (role "control", 10 facts, deliberately
opposite on most traits) exists only to define probes and can never be
studied - `get_study_facts()` raises for a control-role entity by
construction, not by convention, so a negative control can't accidentally
get contaminated by a caller forgetting a rule. Two probe kinds:
`recall_probes` are `(prompt, target)` continuation pairs for the fast,
quantitative loss-delta measurement; `generalization_probes` are open
questions for a slower qualitative read, not part of the loss
computation - same two-tier split `train_reconstruction_adapter.py`
already used successfully.

**Ported `src/piper_geometry/extractor.py`** from
`feature/reasoning-geometry` - `main` only ever had an empty placeholder
there. `ResidualExtractor` is genuinely general-purpose infrastructure,
not specific to that branch's research question, so this branch needed
its own copy rather than merging the whole (much larger, unrelated)
reasoning-geometry history.

**`embeddings`** (`src/piper_memory/embeddings.py`) - the two embedding
methods from yesterday's "try both in parallel" plan.
`SmallModelEmbedder` wraps `all-MiniLM-L6-v2`, purpose-built for
retrieval. `QwenHiddenStateEmbedder` repurposes Qwen's own hidden state
at layer 18 (reusing `ResidualExtractor` as-is) - an emergent by-product
of a next-token-prediction objective, with the well-earned low confidence
about any single layer this project's cross-model work already
surfaced. `SmallModelEmbedder` got real (not mocked) verification - it's
small and CPU-friendly enough to run locally, unlike Qwen/Phi-4-mini.
Confirmed the correct 384-dim output and a genuine semantic-sanity check:
two similarly-structured fictional-animal-fact sentences (warbles,
quaddles) scored higher in cosine similarity (0.447) than either did
against an unrelated sentence (0.330) - real evidence of structure, not
just "it ran." `QwenHiddenStateEmbedder` tested with a synthetic fake,
matching the established pattern for `ResidualExtractor`-dependent code.

**`loss_measurement`** (`src/piper_memory/loss_measurement.py`) - the
core "did this help" signal. `compute_probe_loss` is one teacher-forced
forward pass, no sampling - simpler than
`train_adapter.py`/`train_reconstruction_adapter.py`'s loss functions
since there's no cross-model injection here, just a normal single-model
forward pass scoring the target continuation's tokens.
`evaluate_recall_probes` averages this across a whole entity's probes.
Position-alignment verified with the same hand-checkable fake-model
technique as `reconstruction_loss_and_accuracy`: a model whose logits
are deterministically tied to position index, proving a correctly-
aligned target scores perfect accuracy while a deliberately shifted-by-
one target scores zero - the test would actually catch a real alignment
bug, not just pass by coincidence.

**`warble_harness`** (`src/piper_memory/warble_harness.py`) - ties
everything together and actually ran, for real, against
Qwen2.5-0.5B-Instruct.

## The real result

Explicitly a plumbing sanity check, not a learning test - the "study"
step here is in-context (facts prepended directly to the prompt), which
yesterday's design discussion already identified as a near-trivial
signal on its own. It proved the infrastructure works end to end
(`MemoryStore` population, real loss measurement, persistence
round-trip all passed) - and it also gave real, quantified teeth to
yesterday's prediction rather than leaving it as theory:

| | before | after | delta | accuracy |
|---|---|---|---|---|
| warbles (own facts in context) | 3.4662 | 0.8715 | **+2.5947** | 0.483 -> 0.825 |
| quaddles (warble context, own facts never shown) | 3.6139 | 2.4856 | **+1.1283** | 0.271 -> 0.523 |

Quaddles improved substantially even though none of its actual facts
were ever shown - just having *any* reasonably coherent text in context
helps prediction, likely generic structural/vocabulary priming rather
than anything fact-specific. Over 40% of warbles' apparent improvement
magnitude shows up on completely unrelated content too. Warbles still
improved more than quaddles (2.59 vs. 1.13 nats), so relevance isn't
fully ignored by whatever's happening - but the confound is large enough
that a naive "did loss improve" check on warbles alone, without the
quaddle control, would have looked like a clean success and been
seriously misleading. This is exactly why the control was built as
structurally-enforced rather than a discipline to remember, and exactly
the reasoning that pointed toward LoRA fine-tuning as the next step
yesterday - now backed by a real number instead of just the prediction.

## Where this stands

All four foundational pieces built, tested, and now proven against a
real model end to end. `QwenHiddenStateEmbedder` wasn't wired into this
first harness pass (scoped down to avoid loading two copies of the same
base model) - a natural, low-effort follow-up once the core plumbing was
proven, which it now has been.

Next: the LoRA fine-tuning study step, to get a genuinely cold
(no-context) post-study measurement - the only way to rule out today's
demonstrated in-context confound and get a signal that actually reflects
persistent, fact-specific learning rather than generic priming.

## LoRA built and run for real: genuine cold learning demonstrated, with a real, partial confound of its own

`finetune_lora` (`src/piper_memory/lora_finetune.py`) via HuggingFace's
`peft` - freezes the base model entirely (same as every other experiment
in this project), injects trainable low-rank matrices alongside the
attention `q_proj`/`v_proj` layers instead of training them directly.
`target_modules` confirmed against Qwen2's actual module names rather
than assumed. Verified against the real, already-cached
Qwen2.5-0.5B-Instruct rather than a mock (PEFT's introspection into real
transformer submodule structure makes faking this one hard, and the
model was already local): base model's own `q_proj` weight confirmed
byte-for-byte unchanged after fine-tuning; LoRA's own parameter tensors
confirmed to move away from initialization; loss on toy facts dropped
from 6.38 to 0.07 over 100 real steps; the tuned model correctly
integrates with `evaluate_recall_probes`, reaching near-perfect cold
recall of exactly what it was just taught.

### The real warble/quaddle result

`run_lora_check` (`warble_harness.py`) - unlike the in-context sanity
check, both before and after measurements are genuinely COLD: no warble
content anywhere in the prompt, either before or after fine-tuning. Any
improvement can only come from the LoRA adapter's own trained weights.

| | before | after | delta | accuracy |
|---|---|---|---|---|
| warbles (LoRA-trained on this) | 3.4662 | 0.8169 | **+2.6492** | 0.483 -> 0.913 |
| quaddles (never trained on) | 3.6139 | 2.9296 | **+0.6844** | 0.271 -> 0.435 |

Warbles improved substantially - almost exactly matching the in-context
run's magnitude (2.65 vs. 2.59) - but this time with zero warble content
in the prompt at measurement time. That's real evidence of persistent,
weight-level learning, not context-priming; there's nothing left in
context for the improvement to be coming from.

Not a clean win, though: quaddles improved meaningfully too (+0.68),
despite never having any of its own facts trained on and despite there
being no context at all to prime from this time. That rules out the
*specific* in-context confound, but reveals a different one - warbles
and quaddles were deliberately written with parallel sentence structure
(same categories: color+type, abilities, diet, social behavior,
communication), so fine-tuning on warble sentences most likely
reinforced the shared *sentence pattern* itself, not just warble-specific
content, and that generalized somewhat into quaddle's structurally
similar probes.

The real, quantified progress: the leak shrank substantially. In-context,
quaddles' improvement was ~44% the size of warbles' - a large confound.
Here, cold with LoRA, it's ~26% - genuine, measured improvement in
specificity, just not full elimination of the confound. A meaningful
first real result for the whole track: LoRA fine-tuning does produce
cold, persistent, *mostly* fact-specific loss improvement - real evidence
for the core hypothesis - while surfacing a genuine, still-open question
about how much of what's learned is content-specific versus
structure-general, and whether/how that's reducible further (more
facts with more varied structure? a different LoRA rank or target
module selection? more training data diversity per entity?).

### A reporting fix, prompted by a sharp catch

The 200-step training run's printed loss bounced between 0.27 and 3.5,
looking unstable. It wasn't - `rng.choice` samples one random fact per
step, and different facts sit at different loss values at any given
moment, so whichever one gets picked dominates the printed number far
more than genuine progress does. `_average_facts_loss` now computes the
true average across all 10 study facts at each reporting checkpoint,
verified against an independently-computed manual average.

### Where this stands

`piper_memory`'s core mechanism is validated: real, measurable,
mostly-specific learning from a genuine weight update, distinguishable
from both memorization-via-context and generic priming, via a clean
fabricated-knowledge control. This track is migrating to a new,
standalone repository (`stvenmobile/curious-george`) from here, to keep
`piper_assistant` focused on its actual job (the Orin NX's live
assistant runtime) and to build the next phase as a proper Colab-based
project - the port carries this tested code forward as its foundation
rather than starting over.
